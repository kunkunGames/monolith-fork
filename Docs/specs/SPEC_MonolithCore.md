### Persistent service activation

Monolith separates version-controlled project policy from local durable operator intent:

| Concern | Hard project-policy gate | Project activation default | Per-user activation | Default and lifecycle |
|---|---|---|---|---|
| MCP HTTP endpoint | `UMonolithSettings::bMcpServerEnabled` | `bServerEnabledByDefault` | `ServerEnabled` | A missing user key inherits the project default. `Monolith.StartServer` validates durable-host and policy gates, persists true, then binds `/mcp` and `/health`; `Monolith.StopServer` persists false, unbinds Monolith routes, and removes the caller-owned sentinel immediately. Durable hosts reconcile externally edited activation after cache revalidation. |
| Source and asset indexing | `bEnableSource`, `bEnableIndex` | `bIndexingEnabledByDefault` | `IndexingEnabled` | A missing user key inherits the project default. `Monolith.StartIndexing` persists true, enables both subsystem hook sets, and requests their cheapest correct catch-up modes. `Monolith.StopIndexing` persists false, removes queued/automatic hooks, and lets an already-active transactional run finish safely. |

The project defaults live in source-controlled `Config/DefaultMonolith.ini`. Console commands write only generated `Saved/Config/<Platform>/Monolith.ini` under `[Monolith.UserActivation]`; Project Settings/default-config saves therefore cannot absorb a user's effective choice. An older `Saved/Monolith/Activation.ini` is consulted only when the matching generated user key is absent, then its explicit values are written to the generated config and the legacy file is retired. A Start command cannot override a false hard project-policy gate. Failed user-config writes are reported and never silently treated as persistent success. Server startup failure after a successful write leaves the desired state true so the next durable editor launch retries. Stop performs the current-process shutdown even if its persistent write fails, while logging that restart safety is not guaranteed.

The editor and offline recovery scripts necessarily resolve this hierarchy independently because the scripts must work without loading Unreal. `Scripts/tests/ActivationParityCases.json` is their shared precedence fixture: `Monolith.Activation.Parity` drives the native resolver with it, while `MonolithActivationParity.Tests.ps1` drives `monolith_activation_state.ps1` with the same cases. This keeps user-over-project precedence, partial overrides, legacy preservation, and malformed fail-closed behavior from drifting between the two implementations.

HTTP shutdown owns only Monolith's registered routes and sentinel. It does not call UE's process-global `FHttpServerModule::StopAllListeners`, which could stop unrelated HTTP services. Consequently `/mcp` and `/health` become unavailable immediately; the shared UE listener and router are retained for unrelated route owners and safe same-port Start/reload. An in-process port move is rejected because UE exposes no per-port listener teardown. Startup preflights an occupied port and distinguishes a router retained by this `FHttpServerModule` from a foreign listener before reporting readiness.

Index activation gates writers and automatic delegates, not database construction or reads. `UMonolithIndexSubsystem` opens `ProjectIndex.db`, and `UMonolithSourceSubsystem` opens `EngineSource.db`, before consulting activation. Read actions and the offline Query executable therefore keep working while indexing is disabled. Source indexing temporarily closes its database while its writer owns the run, as it did before this feature.

The `/health` response adds `server_activation_enabled` and `indexing_activation_enabled`. The core `monolith.reindex`, source reindex actions, and `bridge.start_indexing` reject or report disabled state without changing it; console commands are the only persistent activation surface. The legacy `Monolith.StartIndex` command remains a full-asset-index alias and does not enable indexing.

### MCP listener startup role gate

`FMonolithCoreModule::StartupModule` registers the action surface before it classifies the current process. The classifier then permits listener and sentinel startup only for a durable editor host, after which durable server activation and the project-policy kill switch must both pass:

| Role token | Classification input | Listener/sentinel contract |
|---|---|---|
| `durable_host` | Persistent editor, including the normal `-NullRHI` headless editor launched for MCP recovery, with none of the bounded-role markers below | May continue through `ServerEnabled` and `bMcpServerEnabled`, bind the configured port, and write the sentinel after a successful start. |
| `commandlet` | `IsRunningCommandlet()==true` | Actions stay registered, but HTTP listener and sentinel startup are skipped. |
| `planned_test_exit` | Bare `-TestExit` or `-TestExit=<condition>` | Actions stay registered, but a process that declares its own exit condition cannot advertise durable MCP readiness. |
| `automation_exec` | A semicolon/comma-separated `-ExecCmds` command starts with the tokens `Automation RunTests` or `Automation RunAll`; token matching is case-insensitive and whitespace-tolerant | Actions stay registered for in-process automation, but listener and sentinel startup are skipped even when the exact project is loaded. The same words inside another command's log prose do not change the role. |

Every non-durable role logs `Monolith — MCP host role=<role>; registered actions and skipped HTTP listener/sentinel startup`. The gate is deliberately role-based rather than a blanket `-ExecCmds` rejection: a persistent editor using unrelated execution commands remains eligible. Shutdown removes `.monolith_running` only when this process successfully wrote it, so a bounded automation/commandlet process cannot delete a durable editor's sentinel during its own exit. Failed deletion retains ownership so a later stop/shutdown can retry. `Monolith.Restart` preserves the current sentinel while routes remain live, rewrites it after a successful same-port rebind, and removes it only if the restart leaves the server stopped. `Monolith.Core.McpHostRole.Classification` covers a persistent editor, persistent NullRHI headless editor, commandlet, `RunTests`, `RunAll`, log-prose non-matches, and `TestExit`; current-run execution evidence belongs in the focused verification record rather than this contract.

Gated by `bEnableAsyncJobs`: with the flag off it returns `{status:"disabled", requested_job_id, cancel_requested:false, reason}`; with the flag on it sets the cooperative cancel flag for cancellable jobs and returns the post-request row. The row remains non-terminal with `cancel_requested:true` until the producer observes the request and acknowledges `cancelled`. Required param: `job_id` (string). |

#### Discover action projection

`monolith_discover(namespace)` is **terse by default**: for each action it returns `action` (name) + a one-line `description` only. The full per-action internal `params` schema and MCP-facing JSON Schema `inputSchema` are NOT emitted by default — fetch a single action's schema with `describe_query action_schema` (the lazy-fetch target, ~54 tokens) or inline every action's schema with `detail=true`. Terse mode cuts per-namespace discover payload by ≥70% vs the pre-change shape (the win is dropping eager schema objects, not truncating the action list).

`monolith_discover(filter="<substring>", limit=N)` omits `namespace` and applies the same action-name/full-description predicate across every registered namespace. It answers "which namespace owns this capability" for a caller that cannot name the namespace yet.

The response carries two views of one filtered set:

- `matched_namespaces` — every namespace containing at least one match, each with a `match_count`, in registry order. Computed **before** pagination, so a small `limit` never narrows it. This is the namespace-selection view: pick a namespace, then call `monolith_discover(namespace="<ns>")` for its full action list.
- `actions` — the paginated flat candidate list, each row carrying `namespace`, `action`, bounded `description`, optional `category`, and optional detailed `params`.

`match_count` is a count of the filtered set, not a relevance score: namespaces are never ordered by it, and no hand-tuned ranking, scoring tier, or alias database is introduced. Registry order is retained throughout, and any semantic ranking remains the MCP client's concern. No-argument discovery remains the namespace inventory and does not carry `matched_namespaces`.

The editor-offline `monolith_discover` seed schemas in `Scripts/monolith_proxy.py`
and `Tools/MonolithProxy/monolith_proxy.cpp` are unchanged by this path and
already lag the live registration (they predate `filter`/`offset`/`limit`).
A cold-start client that has never seen a live `tools/list` therefore cannot
construct the cross-namespace call until the Editor is reachable. Refreshing the
proxy seeds is tracked separately from this discovery contract.

**One-line description trim (terse only).** Each `description` is trimmed to its first sentence (sentence terminator at index ≥25 followed by a space or end-of-string), else hard-capped at 150 chars on a word boundary, with an ASCII `"..."` suffix appended when trimmed; already-short descriptions are returned verbatim (no suffix). The FULL untrimmed description is preserved in detail mode and via `describe_query action_schema`.

**Optional params:**

| Param | Type | Default | Meaning |
|-------|------|---------|---------|
| `detail` | bool | `false` (terse) | `true` inlines every action's full `params` schema — reproduces the pre-change response shape byte-for-byte (`action`/`description`/`category`/`params` per action). Canonical flag. |
| `verbose` | bool | unset | Accepted ALIAS for `detail` (read only when `detail` is unset). `verbose=true` == `detail=true`. |
| `filter` | string | — | Case-insensitive substring matched against the action name OR the FULL description. Applied after any `category` filter, before pagination. |
| `offset` | int | `0` | Pagination start after `category`/`filter`, clamped to `[0, total]`. |
| `limit` | int | `50` | Pagination page size. Values below 1 are normalized to the bounded default page size; positive values clamp to the action-list max (currently 1000). |

**Top-level response fields:** `total` (always; post-filter count); `truncated`; `limits` (`default_limit`, `max_limit`, `limit`, `requested_limit`, `offset`, `total`, `returned`); `next_offset` / `next_cursor` when more rows remain; `schema_hint` (terse only). The `schema_hint` string is: `Param schemas omitted. Call describe_query(action_schema, target_namespace="<ns>", target_action="<name>") for one action's full schema, or pass detail=true to inline all.`

**Unchanged:** `discover()` with no namespace, filter, or positive limit still returns the namespace inventory. `describe_query action_schema` remains the lazy-fetch target for a single action's full schema.
